Проект посвящён анализу договоров с проверяемыми доказательными цитатами.
Пользователь отправляет текст договора, а сервис находит юридически значимые условия, возвращает структурированный ответ и указывает фрагменты договора, на которых основан результат.
Проект не является обычной генерацией ответа по всему тексту: сначала строится измеримый поиск доказательных фрагментов, а RLM/DSPy-слой используется как агентная надстройка для навигации по найденным частям документа.

## 2. Постановка задачи и контекст

1. **Предметная область и задача:**
   - решается задача поиска и извлечения юридически значимых условий из договоров;
   - потенциальный пользователь сервиса загружает договор и получает аналитику по интересующим типам условий, например применимое право, ограничение ответственности или запрет уступки прав;
   - основной результат должен быть не просто текстовым ответом, а ответом с проверяемыми цитатами и символьными смещениями в исходном договоре.

2. **Формулировка задачи в терминах ML/ИИ:**
   - входные данные: текст договора и список типов условий;
   - промежуточная задача: найти фрагменты договора, пересекающиеся с эталонными доказательствами;
   - выход модели: ранжированный список фрагментов-кандидатов и JSON-ответ по каждому типу условия;
   - ограничения: нельзя строить запрос из эталонного текста доказательства, нельзя смешивать поле ответа CUAD `*-Answer` с доказательными фрагментами, каждый найденный ответ должен иметь цитату.

3. **Целевые метрики качества:**
   - полнота на первых k результатах (Recall@1, Recall@3, Recall@5, Recall@10);
   - средний обратный ранг (MRR);
   - покрытие эталонных доказательств после нарезки договора на фрагменты;
   - для ранжировщика также используются площадь под ROC-кривой (ROC AUC) и средняя точность (Average precision).

Эти метрики выбраны потому, что для сервиса важнее всего быстро поднять доказательный фрагмент в верхние результаты, а не просто сгенерировать правдоподобный текст.

## 3. Данные

1. **Источник данных:**
   - CUAD используется как основной набор данных для извлечения условий из договоров;
   - ContractNLI используется как дополнительный набор данных для проверки утверждений по договорам;
   - Ru-Legal-QA-v1 используется как реальный русскоязычный набор юридических вопросов с полными текстами нормативных актов и цитатами-основаниями;
   - ЕИС БТК используется как открытый источник типовых контрактов и типовых условий Единой информационной системы закупок для слабой разметки разделов;
   - исходные архивы CUAD и ContractNLI лежат в `data/raw/cuad/CUAD_v1.zip` и `data/raw/contractnli/contract-nli.zip`.

2. **Структура данных:**
   - после обработки создаются `contracts.jsonl`, `clause_examples.jsonl`, `nli_examples.jsonl`, `chunks.jsonl`, `splits.json`;
   - текущий обработанный слой содержит 1198 документов и договоров, 4914 примеров условий и русскоязычных вопросов с цитатами, 10319 примеров ContractNLI и 35352 фрагмента;
   - отдельный слой Ru-Legal-QA-v1 содержит 81 документ, 324 примера вопроса с цитатами, 2161 цитатный спан и 44302 фрагмента;
   - сборщик ЕИС БТК сохраняет тексты и слабую разметку, если портал доступен из текущей сети; при сетевой ошибке причина фиксируется в `artifacts/eis_btk_summary.json`;
   - для каждого фрагмента хранятся `char_start`, `char_end`, текст и номер фрагмента внутри договора.

3. **Предобработка и EDA:**
   - договоры нормализуются в единую JSONL-схему;
   - договоры режутся на фрагменты по словам с перекрытием, при этом текст фрагмента берётся срезом исходного договора, чтобы сохранить точные смещения;
   - для CUAD поле `*-Answer` хранится отдельно как `answer_value` и не используется как доказательство;
   - покрытие эталонных доказательств после нарезки составило 0.998.

Основные шаги разведочного анализа данных лежат в `notebooks/01_eda.ipynb` и `reports/eda/`.

## 4. Модели и подходы

1. **Базовые модели:**
   - простая базовая линия: брать первые фрагменты договора;
   - частотный поиск (TF-IDF) по запросу, построенному из типа условия и заранее заданных синонимов;
   - вероятностный лексический поиск (BM25) по тем же запросам.

2. **Улучшенные модели и эксперименты:**
   - поверх кандидатов TF-IDF и BM25 строится таблица признаков;
   - признаки включают оценки и ранги TF-IDF/BM25, покрытие терминов запроса, число юридических маркеров, длину фрагмента, относительную позицию, количество чисел, дат и денежных сумм;
   - финальная улучшенная модель: логистическая регрессия (`LogisticRegression`) с балансировкой классов.

3. **RLM/DSPy-слой:**
   - добавлены инструменты для поиска, чтения фрагмента, чтения соседей и поиска по регулярному выражению;
   - добавлены сигнатуры DSPy для планирования поиска, оценки доказательства и структурирования ответа;
   - добавлена DSPy-программа для оценки доказательств и структурирования ответа;
   - добавлен отдельный скрипт оптимизации через GEPA: `uv run ci_optimize_gepa`;
   - модель-студент задаётся через поставщика LiteLLM: `LITELLM_API_BASE=https://litellm.g-309.ru/v1` и `RLM_STUDENT_MODEL=openai/gemma-4-e4b`;
   - большая учительская модель OpenRouter задаётся через `OPENROUTER_API_KEY` и `RLM_TEACHER_MODEL`;
   - без ключа к большой языковой модели сервис продолжает работать через лексический поиск и ранжировщик.

## 5. Экспериментальный протокол и результаты

1. **Экспериментальный протокол:**
   - запрос для поиска строится только из типа условия и словаря синонимов;
   - релевантный фрагмент определяется через пересечение с эталонным доказательством;
   - ранжировщик обучается на кандидатах TF-IDF и BM25;
   - отложенная часть для ранжировщика строится детерминированно по идентификатору договора.

2. **Сравнение моделей по метрикам:**

   | Модель / конфигурация | Описание | Recall@1 | Recall@5 | Recall@10 | MRR |
   |-----------------------|----------|----------|----------|-----------|-----|
   | Первые фрагменты | Простая базовая линия | 0.097 | 0.453 | 0.718 | 0.251 |
   | TF-IDF | Частотный лексический поиск | 0.812 | 0.966 | 0.987 | 0.877 |
   | BM25 | Вероятностный лексический поиск | 0.813 | 0.966 | 0.986 | 0.877 |
   | BM25 + TF-IDF + ранжировщик | Повторное ранжирование кандидатов моделью на признаках | 0.815 | 0.968 | 0.998 | 0.883 |

   Дополнительные метрики ранжировщика на отложенной части: ROC AUC = 0.904, средняя точность = 0.750.

   Отдельная проверка на реальном русскоязычном наборе Ru-Legal-QA-v1:

   | Модель / конфигурация | Recall@1 | Recall@5 | MRR |
   |-----------------------|----------|----------|-----|
   | Первые фрагменты | 0.525 | 0.870 | 0.662 |
   | TF-IDF | 0.639 | 0.920 | 0.765 |
   | BM25 | 0.664 | 0.932 | 0.778 |

   Покрытие цитат Ru-Legal-QA-v1 после нарезки составило 0.999. Это подтверждает, что русскоязычный эксперимент построен на реальных цитатах из датасета, а не на синтетических примерах.

   Дополнительно проверен RLM/DSPy на сложных случаях: из 324 примеров базовая линия (baseline) при `top_k=3` промахнулась по 83. На этих 83 ошибках RLM при `top_k=10`, то есть агентный режим с чтением расширенного набора кандидатов, поднял долю кандидатов с правильной цитатой с 0.000 до 0.675, а долю финальных ответов `found=true` с правильной цитатой — с 0.000 до 0.301. Это показывает, что RLM полезен именно как навигатор поверх расширенного поиска (retrieval), а не как его замена.

   Для демонстрации дополнительно собран валидационный набор из 24 примеров Ru-Legal-QA-v1. Правило отбора не использует RLM: набор смешивает 21 сложный пример, где базовая линия (baseline) при `top_k=3` не поддерживает ответ правильной цитатой, и 3 примера, где поддерживает; правильная цитата во всех случаях есть среди кандидатов при `top_k=10`. На этом наборе поддержка ответа базовой линии равна 0.125, поддержка ответа RLM равна 0.708, наличие правильной цитаты в evidence RLM равно 1.000. Набор сохранён в `data/processed/rlm_validation_examples.jsonl`, сводка — в `artifacts/rlm_validation_summary.json`.

3. **Выбор финальной модели:**
   - финальным вариантом выбран конвейер BM25 + TF-IDF + логистическая регрессия на признаках;
   - он сохраняет воспроизводимость и интерпретируемость, быстро обучается и улучшает качество ранжирования;
   - RLM/DSPy рассматривается не как замена поиска, а как слой навигации и структурирования поверх найденных доказательств.

## 6. Архитектура решения и сервис

1. **Архитектура пайплайна:**

   ```text
   текст договора
     -> нарезка на фрагменты с символьными смещениями
     -> TF-IDF и BM25
     -> ранжировщик на признаках
     -> структурированный JSON-ответ с цитатами
   ```

2. **API и endpoints:**
   - реализованы `GET /health` и `POST /predict`;
   - `/predict` принимает `contract_text`, `clause_types`, `top_k`, `use_rlm`;
   - ответ содержит идентификатор договора, список результатов, цитаты, смещения, оценку уверенности и версию модели.

3. **Технологический стек:**
   - Python, Pydantic, scikit-learn, FastAPI, DSPy;
   - зависимости устанавливаются через `uv`;
   - запуск сервиса: `uv run ci_service` или `uv run ci_service_dev`;
   - запуск в контейнере: `docker compose up --build`.

## 7. Наблюдаемость, конфигурация и безопасность

1. **Логи и наблюдаемость:**
   - есть endpoint `/health`, который показывает статус сервиса и версию модели;
   - smoke-тесты проверяют, что `/predict` реально вызывает конвейер поиска и возвращает доказательные цитаты.

2. **Конфигурации:**
   - параметры данных, поиска, ранжировщика и сервиса вынесены в `configs/`;
   - пример переменных окружения находится в `configs/.env.example`.

3. **Безопасность:**
   - реальные секреты не нужны для режима без RLM;
   - ключи для внешних моделей не добавляются в репозиторий;
   - пользовательский договор обрабатывается в памяти конвейера времени выполнения (runtime pipeline).
