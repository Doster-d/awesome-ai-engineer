# Итоговый проект по курсу «Инженерия Искусственного Интеллекта»

В этой папке находится итоговый мини-проект по курсу.  
Проект должен демонстрировать применение методов и инструментов инженерии ИИ: работу с данными, модели, пайплайны, сервис, эксперименты и (по возможности) воспроизводимость.

- **Краткое описание (2-4 предложения):**
  Проект реализует конвейер поиска доказательных фрагментов (evidence-aware retrieval pipeline) для анализа договоров. Пользователь отправляет текст договора, система режет его на фрагменты, ищет релевантные доказательства через частотный поиск (TF-IDF) и вероятностный лексический поиск (BM25), ранжирует кандидатов моделью на признаках (feature ranker) и возвращает структурированную аналитику в формате JSON с цитатами и символьными смещениями (char offsets).

## 2. Структура проекта

Проект организован в следующей структуре:

- `pyproject.toml` – зависимости проекта (библиотеки Python, необходимые для запуска).
- `report.md` – отчёт по проекту (постановка задачи, данные, эксперименты, результаты).
- `self-checklist.md` – чеклист самопроверки проекта перед сдачей.
- `notebooks/` – экспериментальные ноутбуки:
  - разведочный анализ данных (EDA), прототипы моделей, отдельные эксперименты.
- `src/` – основной код проекта:
  - модули для работы с данными;
  - обучение моделей;
  - запуск сервиса/скриптов.
- `data/` – демонстрационные/учебные данные:
  - **только открытые или обезличенные данные;**
  - при необходимости – небольшие выборки для быстрого запуска.
- `configs/` – конфигурационные файлы:
  - `.yaml`, `.json`, `.env.example` и т.п.
- `tests/` – тесты (юнит-тесты, простые проверки).
- `artifacts/` – сохранённые модели, отчёты, результаты экспериментов.

Дополнительная структура рабочего кода:

- `src/contract_inspector/data/` – схемы, ввод-вывод JSONL (I/O), нормализация CUAD/ContractNLI, сборка обработанных данных.
- `src/contract_inspector/features/` – нарезка на фрагменты, запросы по типам условий, признаки для поиска.
- `src/contract_inspector/retrieval/` – простая базовая линия, частотный поиск (TF-IDF), вероятностный лексический поиск (BM25), оценка качества.
- `src/contract_inspector/models/` – модель ранжирования на признаках (feature ranker) и обучение.
- `src/contract_inspector/service/` – сервис FastAPI и конвейер времени выполнения (runtime pipeline).
- `src/contract_inspector/rlm/` – инструменты, сигнатуры и навигатор для слоя RLM/DSPy.

## 3. Требования и установка

### 3.1. Требования

- язык Python `>= 3.13`.
- `uv` для установки зависимостей и запуска команд.

```bash

```

Загрузка данных:

```bash

```

Исходные архивы ожидаются в:

```text

```

Оптимизация RLM/DSPy через GEPA:

```bash
export OPENROUTER_API_KEY="<ключ OpenRouter>"
export LITELLM_API_KEY="<ключ LiteLLM>"
export LITELLM_API_BASE="https://litellm.g-309.ru/v1"
export RLM_STUDENT_MODEL="openai/gemma-4-e4b"
export RLM_TEACHER_MODEL="<большая учительская модель OpenRouter>"
uv run ci_optimize_gepa --auto light --limit 80
```

Если `LITELLM_API_KEY` не задан, `/predict` с `use_rlm=true` будет использован лексический поиск и ранжировщик.
Пример переменных окружения лежит в `example.env`.

### 4.2. Запуск сервиса через программный интерфейс (API)

```bash
cd project
uv run uvicorn contract_inspector.service.api:app --reload
```

Альтернативно через консольный скрипт:

```bash
uv run ci_service
```

Запуск через Docker Compose:

```bash
docker compose up --build
```

Сервис поднимается на `http://127.0.0.1:8000`.

Конечные точки (endpoints):

- `GET /health`
- `POST /predict`

Пользовательский интерфейс Swagger (Swagger UI):

```text
http://127.0.0.1:8000/docs
```

Пример `curl`:

```bash
curl -X POST "http://127.0.0.1:8000/predict" \
  -H "Content-Type: application/json" \
  -d '{
    "contract_text": "This Agreement shall be governed by the laws of New York. The aggregate liability of either party is capped at fees paid in the prior twelve months.",
    "clause_types": ["Governing Law", "Cap On Liability"],
    "top_k": 3,
    "use_rlm": false
  }'
```

## 5. Данные

Используются открытые датасеты:

- CUAD – основной минимально жизнеспособный продукт (MVP) для извлечения условий (clause extraction).
- ContractNLI – дополнительный трек для NLI-гипотез.
- Ru-Legal-QA-v1 – реальный русскоязычный набор юридических вопросов с полными текстами нормативных актов и цитатами-основаниями.
- ЕИС БТК – открытый реестр типовых контрактов и типовых условий Единой информационной системы закупок; в проекте добавлен сборщик слабой разметки по разделам.

После `build_processed` создаются:

- `data/processed/contracts.jsonl`
- `data/processed/clause_examples.jsonl`
- `data/processed/nli_examples.jsonl`
- `data/processed/chunks.jsonl`
- `data/processed/splits.json`
- `data/processed/ru_legal_qa.contracts.jsonl`
- `data/processed/ru_legal_qa.clause_examples.jsonl`
- `data/processed/ru_legal_qa.chunks.jsonl`
- `data/processed/eis_btk.contracts.jsonl`
- `data/processed/eis_btk.clause_examples.jsonl`
- `data/processed/eis_btk.chunks.jsonl`

Краткая статистика текущего слоя обработанных данных:

- `1198` документов и договоров;
- `4914` примеров условий и русскоязычных вопросов с цитатами;
- `10319` примеров ContractNLI;
- `35352` фрагмента в общем обработанном слое.

Отдельный русскоязычный слой Ru-Legal-QA-v1 содержит 81 документ, 324 примера вопроса с цитатами и 44302 фрагмента.
Он используется для проверки русскоязычного сценария поиска доказательной цитаты по юридическому вопросу.

Сборщик ЕИС БТК работает с открытыми ссылками из `data/raw/eis_btk_urls.txt`.
Если портал недоступен из текущей сети, то причина ошибки хранится в `artifacts/eis_btk_summary.json`.

Разведочный анализ данных (EDA) лежит в `notebooks/01_eda.ipynb` и `reports/eda/`.

На защите я:

1. Покажу структуру `src/contract_inspector/` и артефакты обработанных данных.
2. Покажу метрики из `artifacts/retrieval_metrics.json` и `artifacts/ranker_metrics.json`.
3. Запущу сервис через `ci_service_dev`.
4. Выполню `/predict` через пользовательский интерфейс Swagger (Swagger UI) или `curl`.
5. Покажу, что ответ содержит цитату (`quote`), символьные смещения (`char_start`, `char_end`), оценку уверенности (`score`) и меняется при изменении текста договора.

Текущие ключевые метрики:

| Эксперимент | Recall@1 | Recall@5 | MRR |
|------------|----------|----------|-----|
| Простая базовая линия: первые фрагменты | 0.097 | 0.453 | 0.251 |
| TF-IDF | 0.812 | 0.966 | 0.877 |
| BM25 | 0.813 | 0.966 | 0.877 |
| BM25 + TF-IDF + ранжировщик | 0.815 | 0.968 | 0.883 |

Русскоязычный набор Ru-Legal-QA-v1:

| Эксперимент | Recall@1 | Recall@5 | MRR |
|------------|----------|----------|-----|
| Простая базовая линия: первые фрагменты | 0.525 | 0.870 | 0.662 |
| TF-IDF | 0.639 | 0.920 | 0.765 |
| BM25 | 0.664 | 0.932 | 0.778 |

Проверка RLM/DSPy на сложных случаях Ru-Legal-QA-v1: из 324 примеров базовая линия (baseline) при `top_k=3` промахнулась по 83. На этих 83 ошибках расширенный RLM-режим с чтением до 10 кандидатов поднял долю кандидатов с правильной цитатой с `0.000` до `0.675`, а долю финальных ответов `found=true` с правильной цитатой — с `0.000` до `0.301`.

Для демонстрации собран отдельный валидационный набор `data/processed/rlm_validation_examples.jsonl`: 24 реальных примера Ru-Legal-QA-v1. Набор смешанный: 21 сложный пример, где базовая линия (baseline) при `top_k=3` не поддерживает ответ правильной цитатой, и 3 примера, где поддерживает; правильная цитата во всех случаях есть среди кандидатов при `top_k=10`. RLM не используется при отборе примеров.
Сводка лежит в `artifacts/rlm_validation_summary.json`: поддержка ответа базовой линии — `0.125`, поддержка ответа RLM — `0.708`, наличие правильной цитаты в evidence RLM — `1.000`.

## 8. Ограничения и дальнейшая работа

В текущей версии инструменты (tools) и сигнатуры (signatures) RLM/DSPy добавлены как агентный слой поверх поиска. Без внешнего ключа к большой языковой модели (LLM) или программному интерфейсу (API) сервис работает через лексический поиск (lexical retrieval) и модель ранжирования на признаках (feature ranker).

Дальше можно добавить:

- полноценные модули DSPy `JudgeEvidence` и `StructureClauseAnswer` в пути выполнения (runtime path);
- трассировку вызовов инструментов (trace tool calls) в ответ `/predict`;
